# how-to-write-rules.md — 意图规格写作规范

## 这是什么

意图规格（rules.md）描述**系统对用户的产品承诺**，让执行者（人或 agent）照着规格逐条验收，不需要任何主观判断。

意图测试不是单元测试。两者的本质区别：

| | 单元测试 | 意图测试 |
|---|---|---|
| **视角** | 代码正确性 | 产品行为是否符合承诺 |
| **操作** | 调用函数/方法 | 描述系统/用户行为 |
| **验收标准** | `assert_eq!` 代码 | 可观察的状态检查项 |
| **执行者** | 编译器 + 测试框架 | 人或 agent |
| **关心的** | 函数返回值 | 文件内容、事件序列、UI 状态 |

---

## 一条意图的结构

```
## 意图 N：<一句话描述系统承诺了什么>

**场景**
用户做了什么操作，系统应该有什么反应。产品经理看得懂就对了。

**前提**
测试夹具：MockLlmExecutor 预设什么、用什么 conversation_id、用户消息内容是什么。
字面量，不能有"某个"、"合法的 X"这种模糊描述。

**操作**
系统/driver 的行为描述。写「driver 执行一轮对话」，不写「调用 run_chat_turn()」。

**验收标准**
执行操作后，逐条可观察的验收检查项。见下方「验收标准怎么写」。
```

## 验收标准怎么写

验收标准是**可观察的状态清单**，执行者照着清单，能用肉眼或命令行独立验证每一条。

**标准问题：一个拿到测试环境、不看代码的人，能否照着这条检查项独立验证？**

### ✅ 正确写法

```
- `messages.jsonl` 存在，文件共 2 行，每行均为合法 JSON
- 第 1 行 `role` 字段值为 `"user"`，`content.text` 字段值为 `"你好吗"`
- 第 2 行 `role` 字段值为 `"assistant"`，`content.text` ��段值为 `"你好"`
- EventBus 中 `TurnCompleted` 的 `outcome` 字段值为 `"Cancelled"`
- EventBus 中 `StreamDone` 不出现
- EventBus 中最后一个事件类型为 `AgentIdle`，`scope` 字段值为 `"primary"`
```

### ❌ 错误写法

```
- assert_eq!(msgs.len(), 2)                          ← 测试代码，不是检查项
- storage.get_messages("conv-id") 返回长度为 2 的列表  ← 方法调用语法
- run_chat_turn 返回 Ok                               ← 代码语法
- turn 在 5s 内结束，不挂起                            ← "不挂起"无法验证
- 对话能正常继续                                       ← 模糊形容词
- outcome == ChatTurnOutcome::Cancelled                ← 内部枚举类型名
```

### 验收标准覆盖三个维度

完整的验收标准应该覆盖：

**1. 事件序列**（系统内部发生了什么）
- EventBus 中哪些事件出现、哪些不出现
- 事件的出现顺序
- 关键字段的精确值

**2. 存储状态**（数据是否正确落盘）
- 文件是否存在
- 文件有几行
- 每行是否为合法 JSON
- 关键字段的精确值

**3. 后续可用性**（系统是否还能正常工作）
- 报错/取消后，下一条消息能否正常发送
- 对话状态是否干净

只有事件验收标准是不够的，必须同时验证存储状态。

## 操作怎么写

操作描述系统或驱动者的行为，不是代码调用。

| ❌ 代码调用 | ✅ 行为描述 |
|---|---|
| 调用 `run_chat_turn(&mut state, &request)` | driver 执行一轮对话 |
| 调用 `cancel_token.cancel_with_reason(CancellationReason::UserCancel)` | 触发取消 |
| 调用 `storage.get_messages("conv-id")` | 读取 `messages.jsonl` 文件 |
| 执行 `cargo test` | 跑测试 |

## 三个核心原则

### 原则一：产品视角，不测实现细节

规格描述的是**系统对用户承诺了什么**，不是系统内部如何做到的。

判断方法：**把这条意图给一个不看代码的产品经理读，他能理解吗？**

| ❌ 实现视角 | ✅ 产品视角 |
|---|---|
| 调用 `apply_permission_mode(Ask, tool_name, DontAsk)` | 在 DontAsk 模式下执行完整 turn，EventBus 中不出现 `PermissionAskRequired` |
| Mock LLM 的 `run_llm_step` 被调用了 2 次 | EventBus 中恰好包含 1 个 `ToolCallExecuting` 和 1 个 `ToolCallCompleted` |
| `outcome == ChatTurnOutcome::Cancelled` | `TurnCompleted` 的 `outcome` 字段值为 `"Cancelled"` |

**协议边界的验收标准必须用序列化后的值**，不用 Rust 枚举类型名。

### 原则二：精确，不用模糊形容词

验收标准里出现以下词，一律替换成具体值：

| 模糊（❌） | 具体（✅） |
|---|---|
| 对话正常继续 | `TurnCompleted` 的 `outcome` 字段值为 `"Success"` |
| 消息被保存 | `messages.jsonl` 共 2 行，第 2 行 `role` 为 `"assistant"` |
| 系统不挂起 | turn 在 5s 内结束（具体超时值） |
| 有错误提示 | EventBus 中出现 `StreamError`，`error` 字段包含 `"401"` |
| 内容完整 | `content.text` 字段值为 `"你好，我是助手"`（精确字符串） |

### 原则三：一条意图只测一件事

意图名里出现"并且"、"同时"，通常要拆分。

❌ 取消后已流出内容落盘且系统可继续使用  
✅ 意图 1：取消后已流出内容落盘  
✅ 意图 2：取消后系统可继续发新消息

## 前提怎么写

前提决定测试是否可复现，必须用字面量，不能有"某个"、"合法的 X"。

| ❌ 模糊 | ✅ 具体 |
|---|---|
| 使用某个对话 | conversation_id 为 `"conv-cancel-test"` |
| 用户消息内容 | 用户消息为 `"请介绍一下自己"` |
| Mock LLM 返回内容 | MockLlmExecutor 预设：先发出 delta `"你好"`，检测到 cancel 后返回 `Cancelled` |
| 合法的 fixture | `name = "薪资分析偏好"`，`description = "用户偏好箱线图"`，`content = "遇到薪酬分析优先建议箱线图"` |

## 写作流程

1. **先想产品承诺**：用户做了 X，系统承诺 Y。不要先看代码。
2. **先写场景和验收标准**：验收标准定义"这条意图在验什么"。先写清楚，再反推前提和操作。
3. **再看代码提取事实**：字段名、序列化值、文件路径、字符串常量——只提取需要的事实，不让代码结构决定意图怎么组织。
4. **用自查清单过一遍**：写完逐项检查。

---

## 快速自查清单

写完一条意图后逐项检查：

- [ ] 场景用产品语言描述了吗？产品经理看得懂？
- [ ] 操作里有没有代码调用？改成行为描述
- [ ] 验收标准里有没有测试代码语法（`assert_eq!`、`.unwrap()`、方法调用）？改成检查项
- [ ] 验收标准里有没有 Rust 枚举类型名？改成序列化后的字符串
- [ ] 验收标准里有没有模糊形容词（"正常"、"正确"、"合适"、"不挂起"）？替换成具体值
- [ ] 验收标准覆盖了存储状态（文件行数、字段值）吗？
- [ ] 验收标准覆盖了后续可用性（报错/取消后系统能否继续工作）吗？
- [ ] 前提里有没有"某个"、"若干条"、"合法的 X"？写出具体字面量
- [ ] 这条意图名里有没有"并且"？能拆就拆
- [ ] 已有意图里有没有覆盖同一个产品承诺的？有就合并

## 常见错误速查

| 错误模式 | 如何识别 | 如何修正 |
|---|---|---|
| **代码调用写进操作** | 操作里有函数名/方法调用 | 改成系统行为描述 |
| **测试代码写进验收标准** | 验收标准里有 `assert_eq!`、`.unwrap()`、变量赋值 | 改成可观察的检查项 |
| **实现视角** | 验收标准中验证了内部方法调用次数/函数名 | 改成 EventBus 事件数量/行为描述 |
| **枚举类型名当检查项值** | 验收标准里写 `SomeEnum::Variant` | 改成序列化后的字符串值 |
| **模糊形容词** | "相关说明"、"正确返回"、"能找到"、"不挂起" | 替换成具体字符串、数量、字段值 |
| **只验证事件，不验证存储状态** | 验收标准全是 EventBus 事件，没有文件状态验证 | 补充 `messages.jsonl` 行数和字段值 |
| **前提 fixture 模糊** | "某工具"、"若干条"、"合法的 X" | 写出具体字面量 |
| **意图太宽** | 意图名里有"并且" | 拆分 |
