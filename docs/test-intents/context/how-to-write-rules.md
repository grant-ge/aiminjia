# how-to-write-rules.md — 意图规格写作规范

写 rules.md 的目标：**让 Codex 拿到规格后不需要任何判断，直接翻译成测试代码。**

---

## 核心原则

意图规格有三个维度，每个维度都有独立的质量标准。

### 维度一：视角——测产品行为，不测实现细节

规格描述的是**系统对用户承诺了什么**，不是系统内部如何做到的。

判断方法：**把这条意图给一个不看代码的产品经理读，他能理解吗？** 能理解说明视角正确。

| 实现视角（❌） | 产品视角（✅） |
|---|---|
| 调用 `apply_permission_mode(Ask, tool_name, DontAsk)` | 在 DontAsk 模式下执行完整 turn，断言 EventBus 中不出现 `PermissionAskRequired` |
| Mock LLM 的 `run_llm_step` 被调用了 2 次 | EventBus 中恰好包含 1 个 `ToolCallExecuting` 和 1 个 `ToolCallCompleted` |
| `outcome == ChatTurnOutcome::Cancelled` | `TurnCompleted` 的 `outcome` 字段序列化值为 `"Cancelled"` |

**特别注意：协议边界的断言必须用序列化后的值**

系统内部用 Rust 枚举，前端和测试验收的是序列化后的字符串。断言内部类型名等于在测实现，不是在测协议。

---

### 维度二：精确度——断言必须能直接写成代码

断言是"可验证的合同"，必须精确到字段值、字符串、数量，让 Codex 不加思考就能写出 `assert_eq!`。

**断言的三个层次（由浅到深）：**

```
1. 模糊（❌）：Deny 消息包含 workspace 相关说明
2. 具体（✅）：Deny 消息包含字符串 "workspace" 且包含工具名 "file_write"
3. 完整（✅+）：逐字段核对 payload 每个字段的值，包括幂等键、兼容字段
```

**协议完整性：不能只断言"关键字段"**

一个事件 payload 的每个字段都是产品承诺。只断言"主字段"会漏掉幂等键、legacy 兼容字段等同等重要的字段。

写完断言后，对照源码中的 payload 构造，逐字段核对是否都有断言覆盖。

例：`tool:completed` 事件的完整断言不止 `toolResult.isError`，还应包括：
- 顶层 `id == msg_id`（消息 upsert 的幂等键）
- 顶层 `role == "tool"`
- 顶层 `content == {}`（空对象，与 toolResult.content 不同）
- `success == !is_error`（legacy 兼容字段）
- `runId`（关联 turn 的字段）

---

### 维度三：可复现性——前提必须是零歧义的 fixture

前提决定测试稳定性。模糊的前提会让 Codex 每次生成不同输入，测试不可复现。

**前提的三个质量要求：**

**1. 字面量代替"某个"**

| 模糊（❌） | 具体（✅） |
|---|---|
| 构造一条合法的 ProjectMemoryEntryDraft | `name = "薪资分析偏好箱线图"`，`description = "用户偏好用箱线图展示薪资分布"`，`content = "遇到薪资分析时优先建议箱线图。"` |
| Mock LLM 预设多次 ToolCalls | Mock LLM：第 1 轮返回 ToolUse（工具名 `dummy_tool`），第 2 轮返回 ContentComplete，输出 `"分析完成"` |

**2. API 调用必须列出全部参数，不能用 `...` 占位**

Codex 无法猜枚举值或参数类型，占位符直接导致编译失败。

❌ `cancel_session(session_id, ...)`  
✅ `cancel_session(&session_id, CancellationReason::UserCancel)`

❌ `SessionRuntime::with_llm_executor(executor)，并传入 RuntimeEventBus`  
✅ `SessionRuntime::with_llm_executor(QueryEngine::default(), RuntimeEventBus::new(), executor)`

**3. 枚举变体分条写，不要在同一个意图里测两个变体**

一条意图里构造两个不同 fixture 验证两个变体，看似简洁，但失败时难以定位，也违反"只测一件事"原则。

❌ 一条意图同时断言 `AgentIdle(Primary)` 和 `AgentIdle(Child)` 各自映射正确  
✅ 拆成：意图 9（Primary scope → "primary"）和意图 10（Child scope → "child"）

枚举变体、true/false、有值/空值，都应该分条写。

## 写作流程

### 第一步：先想清楚产品承诺，再看代码

从用户能感知的行为出发，列出这个功能对用户承诺了什么：
- 用户做了 X 操作，系统应该有 Y 反应
- 系统在 Z 条件下，应该表现为 W

然后带着这些问题去读代码，只提取需要的事实（边界值、字段名、字符串常量），不让代码结构决定意图的组织方式。

### 第二步：一条意图只测一件事

意图名里出现"并且"、"同时"通常意味着应该拆分。

❌ 意图太宽：保存记忆时写入文件并重建索引，且重复保存时覆盖不复制  
✅ 拆分后：  
- 意图 1：保存记忆时写入独立 entry 文件并重建索引  
- 意图 6：同名记忆重复保存时更新而不是复制

### 第三步：先写场景和断言，再补前提和操作

场景和断言定义"这条意图在测什么"。先把这两块写清楚，再反推需要什么前提和操作。

顺序写错容易出现"写完前提才想到断言"——导致测试跟着实现走，而不是跟着规格走。

---

## 分层原则

复杂系统的意图规格按层分开写，每层只测自己那一层的承诺：

```
服务层（数据模型与持久化）
  ↓
工具层（LLM 调用的接口行为）
  ↓
Turn 注入层（与对话驱动器的集成）
```

层之间不测对方的内部实现。工具层测"LLM 调用后返回什么"，不测"文件是否落盘"（那是服务层的责任）。

主流程意图（1-5）和边界意图（6+）分开写。不要把"损坏 entry 跳过""空 query 不召回"这类边界条件混进主流程意图。

## 常见错误模式速查

这些模式在 review 中反复出现，写完意图后逐一检查：

| 错误模式 | 如何识别 | 如何修正 |
|---|---|---|
| **实现视角** | 断言了内部方法调用次数 / 直接引用内部函数名 | 改成 EventBus 事件数量 / 行为描述 |
| **枚举类型名当断言值** | 断言里写 `SomeEnum::Variant` | 改成序列化后的字符串值 |
| **API 参数用占位符** | 前提里有 `...` 或"并传入 X" | 补全所有参数和具体枚举值 |
| **同一意图多个变体** | 前提里构造了 2 个不同 fixture | 拆成两条独立意图 |
| **payload 只断言关键字段** | 只断言 1-2 个字段 | 对照源码逐字段补全 |
| **断言用模糊形容词** | "相关说明"、"正确返回"、"能找到" | 替换成具体字符串、数量、字段值 |
| **前提 fixture 模糊** | "某工具"、"若干条"、"合法的 X" | 写出具体字面量 |
| **意图太宽** | 意图名里有"并且" | 拆分 |
| **重复覆盖同一承诺** | 两条意图本质上测同一件事 | 合并 |

## 快速自查清单

写完一条意图后逐项检查：

- [ ] 场景描述里有没有内部 API 名称？改成行为描述
- [ ] 断言里有没有 Rust 枚举类型名？改成序列化后的字符串
- [ ] 断言里有没有"方法被调用 N 次"？改成 EventBus 中对应事件的数量
- [ ] 断言里有没有模糊形容词（"相关"、"正确"、"合适"）？替换成具体值
- [ ] 断言有没有逐字段核对源码的 payload 构造？幂等键和 legacy 兼容字段也要覆盖
- [ ] 前提里有没有 `...` 占位参数？补全所有参数（包括枚举值）
- [ ] 前提里有没有"某工具"、"若干条"、"合法的 X"？写出具体字面量
- [ ] 这条意图里有没有两个不同 fixture（如两个枚举变体）？拆成两条
- [ ] 这条意图能不能拆成两条更小的？能就拆
- [ ] 已有意图里有没有覆盖同一个产品承诺的？有就合并
