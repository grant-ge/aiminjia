# how-to-write-rules.md — 意图规格写作规范

## 这是什么

意图规格（rules.md）描述**系统对用户的产品承诺**，让执行者（人或 agent）照着规格逐条验收，不需要任何主观判断。

意图测试是**真实的端到端测试**：启动真实应用，执行者在真实界面上操作，读取真实磁盘文件验证结果。

| | 单元测试 | 意图测试 |
|---|---|---|
| **启动方式** | `cargo test` | 启动真实应用 |
| **操作方式** | 调用函数/方法 | 在 UI 上点击、输入、发送 |
| **前提搭建** | 代码写 fixture | 执行者在应用里操作出来 |
| **验收标准** | `assert_eq!` 代码 | 可观察的状态检查项 |
| **验证方式** | 测试框架断言 | 读文件、看 UI、查事件 |

---

## 一条意图的结构

```
## 意图 N：<一句话描述系统承诺了什么>

**场景**
用户做了什么操作，系统应该有什么反应。产品经理看得懂就对了。

**前提**
执行者需要在真实应用里操作出来的初始状态。
写清楚：应用处于什么状态、用什么账号/配置、当前对话里有什么内容。
不写 Mock、不写 fixture 代码、不写 conversation_id 字面量。

**操作**
执行者在真实应用 UI 上的具体动作。
写「在输入框输入 X，点击发送」「在 AI 输出过程中点击停止按钮」。

**验收标准**
操作完成后，执行者逐条检查的可观察状态。
见下方「验收标准怎么写」。
```

## 验收标准怎么写

验收标准是**可观察的状态清单**，执行者照着清单，能用肉眼或命令行独立验证每一条。

**标准问题：一个拿到运行中的应用、不看代码的人，能否照着这条检查项独立验证？**

### ✅ 正确写法

```
- 前端出现错误提示，提示内容包含「认证」「key」「401」之一
- `~/.renlijia/users/{scope}/conversations/{conv_id}/messages.jsonl` 存在，文件共 2 行，每行均为合法 JSON
- 第 1 行 `role` 字段值为 `"user"`，`content.text` 字段值为 `"你好"`
- 第 2 行 `role` 字段值为 `"assistant"`，`content.text` 不为空
- EventBus 中 `TurnCompleted` 的 `outcome` 字段值为 `"Cancelled"`
- EventBus 中 `StreamDone` 不出现
```

### ❌ 错误写法

```
- assert_eq!(msgs.len(), 2)                          ← 测试代码
- storage.get_messages("conv-id") 返回长度为 2        ← 方法调用
- MockLlmExecutor 预设：返回 Cancelled               ← Mock 操作
- turn 在 5s 内结束，不挂起                            ← 无法验证
- 对话能正常继续                                       ← 模糊形容词
```

### 验收标准覆盖三个维度

**1. UI 状态**（用户看到了什么）
- 前端出现了什么提示、按钮状态、内容展示

**2. 存储状态**（数据是否正确落盘）
- `~/.renlijia/` 下的文件是否存在
- 文件有几行
- 每行是否为合法 JSON
- 关键字段的精确值

**3. 后续可用性**（系统是否还能正常工作）
- 报错/取消后，下一条消息能否正常发送
- 对话状态是否干净

## 前提怎么写

前提描述**执行者需要在真实应用里操作出来的初始状态**，不是代码 fixture。

| ❌ 错误写法 | ✅ 正确写法 |
|---|---|
| `MockLlmExecutor 预设：返回 ContentComplete` | 应用已启动，使用有效 API key |
| `conversation_id 为 "conv-test-001"` | 新建一个空对话 |
| `TurnConfigOverrides { max_iterations: Some(2) }` | 在设置中将最大轮次调整为 2 |
| `使用隔离存储` | 使用测试账号，对话历史为空 |

**前提只描述状态，不描述怎么实现这个状态。**

---

## 操作怎么写

操作描述执行者在真实 UI 上的具体动作。

| ❌ 代码调用 | ✅ 真实操作 |
|---|---|
| 调用 `run_chat_turn(&mut state, &request)` | 在输入框输入消息，点击发送按钮 |
| 调用 `cancel_token.cancel_with_reason(...)` | 在 AI 流式输出过程中点击「停止」按钮 |
| 调用 `storage.get_messages("conv-id")` | 查看 `messages.jsonl` 文件内容 |
| 触发取消 | 点击「停止」按钮 |

## 三个核心原则

### 原则一：产品视角，不测实现细节

规格描述的是**系统对用户承诺了什么**，不是系统内部如何做到的。

判断方法：**把这条意图给一个不看代码的产品经理读，他能理解吗？**

| ❌ 实现视角 | ✅ 产品视角 |
|---|---|
| MockLlmExecutor 返回 401 错误 | 配置无效 API key 后发消息，前端出现认证失败提示 |
| `outcome == ChatTurnOutcome::Cancelled` | `TurnCompleted` 的 `outcome` 字段值为 `"Cancelled"` |
| `cancel_token.cancel()` 被调用 | 用户点击停止按钮后，流式输出停止 |

### 原则二：精确，不用模糊形容词

| 模糊（❌） | 具体（✅） |
|---|---|
| 对话正常继续 | `TurnCompleted` 的 `outcome` 字段值为 `"Success"` |
| 消息被保存 | `messages.jsonl` 共 2 行，第 2 行 `role` 为 `"assistant"` |
| 有错误提示 | 前端出现错误提示，包含「401」或「认证」 |
| 内容不丢失 | 第 2 行 `content.text` 不为空 |

### 原则三：一条意图只测一件事

意图名里出现"并且"、"同时"，通常要拆分。

❌ 停止后内容落盘且系统可继续使用
✅ 意图 1：停止后已流出内容落盘
✅ 意图 2：停止后系统可继续发新消息

## 写作流程

1. **先想产品承诺**：用户做了 X，系统承诺 Y。不要先看代码。
2. **先写场景和验收标准**：验收标准定义「这条意图在验什么」。先写清楚，再反推前提和操作。
3. **再看代码提取事实**：字段名、序列化值、文件路径——只提取需要的事实。
4. **用自查清单过一遍**：写完逐项检查。

---

## 快速自查清单

写完一条意图后逐项检查：

- [ ] 场景用产品语言描述了吗？产品经理看得懂？
- [ ] 前提里有没有 Mock / fixture 代码？改成真实应用状态描述
- [ ] 操作里有没有代码调用？改成 UI 上的真实动作
- [ ] 验收标准里有没有测试代码语法（`assert_eq!`、`.unwrap()`、方法调用）？改成检查项
- [ ] 验收标准里有没有 Rust 枚举类型名？改成序列化后的字符串
- [ ] 验收标准里有没有模糊形容词（"正常"、"正确"、"合适"、"不挂起"）？替换成具体值
- [ ] 验收标准覆盖了存储状态（文件行数、字段值）吗？
- [ ] 验收标准覆盖了后续可用性（报错/取消后系统能否继续工作）吗？
- [ ] 前提里有没有"某个"、"若干条"？写出具体状态
- [ ] 这条意图名里有没有"并且"？能拆就拆
- [ ] 已有意图里有没有覆盖同一个产品承诺的？有就合并

## 常见错误速查

| 错误模式 | 如何识别 | 如何修正 |
|---|---|---|
| **Mock 操作写进前提** | 前提里有 `MockLlmExecutor`、`fixture`、`预设` | 改成真实应用状态 |
| **代码调用写进操作** | 操作里有函数名/方法调用 | 改成 UI 真实动作 |
| **测试代码写进验收标准** | 验收标准里有 `assert_eq!`、`.unwrap()` | 改成可观察的检查项 |
| **实现视角** | 验收标准验证了内部函数调用 | 改成 UI 状态或文件状态 |
| **枚举类型名当检查项值** | 验收标准里写 `SomeEnum::Variant` | 改成序列化后的字符串值 |
| **模糊形容词** | "正确返回"、"不挂起"、"正常继续" | 替换成具体值 |
| **只验证事件，不验证存储** | 验收标准全是 EventBus，没有文件验证 | 补充 `messages.jsonl` 行数和字段值 |
| **意图太宽** | 意图名里有"并且" | 拆分 |
