# rules.md — 钉钉渠道（Channel · DingTalk）意图测试规格

## 测试范围
覆盖钉钉作为对外消息渠道的端到端链路：用户在前端绑定钉钉应用，钉钉端收到的消息触发后端建立对话并跑 AI，AI 回复通过钉钉 card 回投到钉钉、超长消息分段、用户在钉钉内的按钮 / 表单交互能正确回传到对话上下文。仅验证渠道编排与消息映射，不覆盖钉钉应用本身的开发者后台配置。

## 待覆盖的主要场景
- 场景 1：用户在前端填入钉钉 AgentId / AppKey / AppSecret 完成绑定，凭据落盘且渠道状态置为已连接
- 场景 2：钉钉端发来一条用户消息，后端自动建立 / 复用一条对话并触发 AI 跑完一个 turn
- 场景 3：AI 文本回复通过钉钉 interactive card 回投到钉钉，内容与对话里持久化的 assistant 消息一致
- 场景 4：单条 AI 回复超过钉钉单卡片长度上限时按段拆分，多张卡片按顺序送达且无内容丢失
- 场景 5：用户在钉钉 card 上点击按钮 / 提交表单，事件回传后作为新的用户输入接入同一对话上下文，AI 能据此继续下一轮
- 场景 6：钉钉凭据失效或推送失败时渠道状态变为异常并在前端明确暴露错误原因，已落盘的对话不丢
- 场景 7：解绑钉钉渠道后凭据被清理，新的钉钉消息不再触发本工作区的 AI 跑动

## 意图 1：用户绑定钉钉后，在钉钉中 @机器人 发消息能触发应用内 AI 对话

**场景**
用户按文档把自己钉钉企业内 AI 机器人的 AppKey / AppSecret / RobotCode 录入到应用，绑定成功之后，在钉钉群里 @这个机器人说一句话，应用端能自动建一条对话、AI 跑完一个 turn，本地 messages.jsonl 里能看到这次问话。

**前提**
- 应用已启动并登录
- 已经准备好一个真实可用的钉钉企业内自建 AI 机器人：AppKey / AppSecret 真实有效，RobotCode 已知
- 当前 LLM 配置正常（应用内对话能正常出回复）
- 「设置 → 渠道 → 钉钉」当前状态为「未配置 / 未连接」（如有旧凭据，先点解绑清掉）
- 准备一个能 @这个机器人的钉钉群，记录群名

**操作**
1. 在「设置 → 渠道 → 钉钉」中填入 AppKey、AppSecret，点击保存绑定
2. 等待页面状态变化（最多 30 秒）
3. 在钉钉里打开准备好的群，发送一条消息 `@机器人 你好，能听到我说话吗？`
4. 等待 60 秒，让消息送达、对话建立、AI 跑完一个 turn
5. 回到应用的对话列表

**验收标准**
- 第 2 步结束后，「设置 → 渠道 → 钉钉」状态文本显示为「已连接 / Connected」（对应后端 `ChannelConnectionState` 序列化值 `"connected"`），无红色错误条
- 第 2 步结束后，钉钉凭据已落盘：`~/.renlijia/users/{scope}/channels/dingtalk/` 或同等目录下存在凭据相关文件（不一定明文存 AppSecret，但配置元数据文件存在）
- 第 4 步结束后，应用对话列表中出现一条新对话，标题或预览中至少包含发送内容 `"你好，能听到我说话吗？"` 的一部分（去掉 `@机器人` 前缀后的实质文本）
- 该对话目录 `~/.renlijia/users/{scope}/conversations/{conv_id}/messages.jsonl` 至少有 2 条记录，第 1 条 `role` 为 `"user"`、`content.text` 中包含 `"你好，能听到我说话吗"` 子串，第 2 条 `role` 为 `"assistant"`、`content.text` 非空
- 该对话的 `conv.json`（或同目录元数据文件）中存在标识来源为钉钉的字段，其值的字符串形式中包含 `dingtalk` 子串（对应后端 `PendingSource::ImDingtalk` 序列化值 `"im-dingtalk"`）

## 意图 2：AI 回复通过钉钉 interactive card 回投，card 内容与应用内对话历史一致

**场景**
钉钉用户问完问题后，AI 的回复要回投到钉钉同一聊天里；卡片里展示的文字应当和应用对话历史里 assistant 消息的文字内容完全一致——不能一边截一半、一边显示完整。

**前提**
- 应用已启动并登录
- 钉钉渠道已绑定且状态为「已连接」（同意图 1）
- 选定一个能 @机器人的钉钉群
- 选一句能让 AI 给出 100~500 字左右的回复的问题（例如 `"@机器人 用三段话介绍一下钉钉机器人接入流程的关键步骤。"`）

**操作**
1. 在钉钉群里发送上述问题
2. 等待最多 90 秒，让机器人在钉钉里回投卡片
3. 在钉钉里完整截屏 / 复制卡片正文（记为 dingtalk_text）
4. 在应用对话列表中找到本次对话，打开
5. 复制 assistant 那条气泡的完整文本（记为 app_text）
6. 打开 `~/.renlijia/users/{scope}/conversations/{conv_id}/messages.jsonl`，找到 `role` 为 `"assistant"` 的最后一条记录，提取 `content.text` 字段（记为 store_text）

**验收标准**
- 钉钉里收到的是一张 interactive card（不是纯文本群消息），有明确的卡片边框和应用机器人头像
- dingtalk_text 与 app_text 字符串完全相等（去掉两端空白字符后用 `diff` 比较一致）
- dingtalk_text 与 store_text 字符串完全相等（去掉两端空白字符后比较一致）
- 卡片内容不为空，且长度 ≥ 50 个字符（说明不是空回复 / 占位卡）
- 应用对话页 assistant 气泡状态显示为「已完成」（非 streaming、非错误），同一条记录在 `messages.jsonl` 中不缺失

## 意图 3：用户解绑钉钉渠道后，新的钉钉消息不再触发 AI，应用内渠道状态变为「未连接」

**场景**
用户在「设置 → 渠道 → 钉钉」点解绑，应用应当把凭据清掉、停掉钉钉拉流、状态归位到未连接；此后再到钉钉群里 @机器人，应用不会再创建新对话、不会再触发 AI。

**前提**
- 应用已启动并登录
- 钉钉渠道当前为「已连接」（绑定流程同意图 1 跑过）
- 至少跑过一轮意图 1 / 意图 2，应用对话列表中已存在至少 1 条 source 为 dingtalk 的历史对话，记录当前对话列表总数为 N_before
- 选定一个能 @机器人的钉钉群

**操作**
1. 在「设置 → 渠道 → 钉钉」点击「解绑」按钮，二次确认
2. 等待 10 秒
3. 检查「设置 → 渠道 → 钉钉」当前状态
4. 在钉钉群里发送 `@机器人 解绑后还能收到吗？`
5. 等待 90 秒
6. 回到应用对话列表，确认列表总数 N_after

**验收标准**
- 第 3 步：状态文本显示为「未配置 / 未连接」（对应后端 `ChannelConnectionState` 序列化值 `"unconfigured"` 或 `"disconnected"` 之一），AppKey / AppSecret 输入框为空（或显示「未绑定」占位）
- 第 3 步：`~/.renlijia/users/{scope}/channels/dingtalk/` 目录下存放凭据的文件已被删除或其中的敏感字段值为空字符串（用 `cat` 或文件浏览器查看）
- 第 6 步：N_after == N_before（没有新对话被创建）
- 第 6 步：所有历史 dingtalk 来源对话仍然存在于列表中（解绑不会删历史数据）；任选一条历史对话打开，其 `messages.jsonl` 文件存在且记录条数与解绑前一致
- 第 4 步发送后到第 5 步结束之间，钉钉群里**未**收到机器人的卡片回复（机器人在解绑后不应再回话）
- 钉钉端可能仍然显示「@机器人」这条消息（钉钉本身不擦消息），但应用日志中不出现因这条新消息触发的 turn 启动记录（搜索 `~/.renlijia/logs/` 最新日志，没有时间戳在解绑之后、内容包含 `"解绑后还能收到吗"` 的 turn 启动 / chat send 行）
