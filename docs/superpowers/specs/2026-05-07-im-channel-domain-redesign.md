# IM Channel Domain Redesign

Date: 2026-05-07
Status: Draft approved for planning
Branch: codex/im-channel-dingtalk-squash

## Background

The current squashed DingTalk IM channel implementation already provides a first pass of:

- IM channel overview page.
- DingTalk card and registration dialog.
- OPEN_CLAW QR registration begin/poll flow.
- Saving AppKey/AppSecret/robotCode and starting a DingTalk stream connection.
- User-scoped channel storage under the current user scope.

The next iteration should not only patch the DingTalk UI. It should reshape the feature into a long-term Channel Domain that can later support Feishu, WeChat, and WeCom without mixing configuration state, enabled intent, and runtime connection state.

This feature has not shipped yet, so no migration from the current temporary `channels/dingtalk_config.json` or `channels/dingtalk_sessions.json` files is required.

## Goals

- Model IM channels as platform states with separate `configured`, `enabled`, and `connection` semantics.
- Keep DingTalk as the only available platform in this phase, while rendering other platforms as coming soon.
- Keep the initial unconfigured state minimal: only a `配置` button, no switch and no more menu.
- Use OPEN_CLAW QR registration for DingTalk configuration.
- After QR registration succeeds, store AppKey, encrypted AppSecret, RobotCode, and metadata in the user-scoped channel directory.
- Do not store or display a robot name. Robot name probing is intentionally out of scope.
- Show AppSecret masked by default. Reveal it only after a second confirmation and only in local dialog state.
- Make connected-state `配置` read-only. It must not start a new QR registration.
- Make `移除` require a second confirmation. Confirming removes credentials and disconnects the channel.
- Make the switch only enable or disable the connection. Turning it off keeps AppKey/AppSecret.
- Keep all persisted data under the current user-isolated directory.

## Non-goals

- No old channel config migration. The feature has not shipped, so new code should only read and write the new structure.
- No robot name fetching or display.
- No manual editable AppKey/AppSecret form in this iteration.
- No deletion of existing chat history when removing platform credentials.
- No full multi-platform runtime implementation beyond a future-proof model and coming-soon states.

## Current Gaps

Current code satisfies the core OPEN_CLAW registration path but misses several product semantics:

- Connected-state `配置` opens the QR registration dialog again instead of a read-only detail dialog.
- `移除` menu item has no implementation.
- The switch opens configuration instead of disabling/enabling a connection.
- `ChannelStatus` mixes configuration and runtime status.
- Frontend store only has `dingtalkStatus`, not a platform state map.
- Backend has no commands for platform config details, reveal secret, enable/disable, or remove.
- Persisted config uses a temporary flat path and schema.

## Domain Model

The backend is the source of truth for platform state. The frontend renders platform cards from this state and sends user intent commands.

```ts
type ChannelPlatform = 'dingtalk' | 'feishu' | 'wechat' | 'wecom'

type ChannelCapability = 'available' | 'comingSoon'

type ChannelConnectionState =
  | 'unconfigured'
  | 'disconnected'
  | 'connecting'
  | 'connected'
  | 'reconnecting'
  | 'configError'

type ChannelPlatformState = {
  platform: ChannelPlatform
  capability: ChannelCapability
  configured: boolean
  enabled: boolean
  connection: ChannelConnectionState
  config?: ChannelConfigView
  lastConnectedAt?: string
  lastError?: string
}
```

Semantics:

- `configured=false`: no credentials exist. The UI shows only a `配置` button.
- `configured=true, enabled=false, connection=disconnected`: credentials exist, but the user has turned the channel off.
- `configured=true, enabled=true`: the channel should run. `connection` reflects the current runtime state.
- `移除` changes `configured` and deletes credentials.
- The switch changes only `enabled` and the connection lifecycle.

### Config View

```ts
type ChannelConfigView = {
  platform: 'dingtalk'
  appKey: string
  appSecretMasked: string
  robotCode: string
  robotCodeSource: 'registration' | 'appKeyFallback'
  source: 'OPEN_CLAW'
  createdAt: string
  updatedAt: string
}
```

`appSecretMasked` should be generated by the backend from the decrypted or encrypted secret without exposing the full secret. The UI can display it safely in store state.

### DingTalk Persisted Config

```json
{
  "schemaVersion": 1,
  "platform": "dingtalk",
  "configured": true,
  "enabled": true,
  "credentials": {
    "appKey": "...",
    "appSecretEncrypted": "..."
  },
  "bot": {
    "robotCode": "...",
    "robotCodeSource": "registration"
  },
  "registration": {
    "source": "OPEN_CLAW"
  },
  "metadata": {
    "createdAt": "...",
    "updatedAt": "..."
  }
}
```

RobotCode rules:

- If DingTalk registration poll returns `robot_code`, store it with `robotCodeSource='registration'`.
- If registration does not return `robot_code`, store AppKey as RobotCode with `robotCodeSource='appKeyFallback'`.
- RobotCode is used by DingTalk card delivery and reply logic.
- Robot name is not fetched and not stored.

## User-scoped Storage

New paths:

- `users/<scope>/channels/dingtalk/config.json`
- `users/<scope>/channels/dingtalk/sessions.json`

The implementation should not read old flat paths:

- `users/<scope>/channels/dingtalk_config.json`
- `users/<scope>/channels/dingtalk_sessions.json`

Because the feature has not shipped, no compatibility migration is needed. A cleanup helper may delete old flat files during initialization to avoid debug confusion, but the new runtime must not depend on them.

AppSecret storage:

- Store only `appSecretEncrypted` on disk when `SecureStorage` is available.
- If secure storage is unavailable, preserve the current fallback behavior only if the app already allows it; the state view must still treat the secret as sensitive.
- Never emit full AppSecret in status events.
- Never store full AppSecret in frontend zustand state.

## UI Behavior

### Unconfigured State

DingTalk card:

- Badge: `未接入`.
- Right side: `配置` button only.
- No switch.
- No more menu.

Clicking `配置` opens DingTalk registration mode.

### Registration Dialog

On open:

- Automatically call `channel_begin_registration('dingtalk')`.
- Render QR from `verificationUriComplete`.
- Show fallback link for users who cannot scan the QR.
- Poll with `channel_poll_registration('dingtalk', deviceCode)` until success, failure, expiration, or timeout.

States:

- `waiting`: show QR and waiting message.
- `error/fail/expired/unknown`: show error and `重新生成二维码`.
- `success`: hide QR, show config summary and connection progress.

After success:

- Backend writes config with `enabled=true` and starts connection.
- Dialog shows AppKey, masked AppSecret, and RobotCode.
- When connected state arrives, show success text and toast `钉钉频道已连接`.

### Connected or Configured Card

When `configured=true`, the DingTalk card shows:

- Badge based on `connection` and `enabled`.
- More menu with `配置` and `移除`.
- Switch reflecting `enabled`.

Suggested labels:

- `connected`: `已连接`.
- `connecting`: `连接中`.
- `reconnecting`: `重连中`.
- `configured=true, enabled=false`: `已配置 / 未连接`.
- `configError`: `配置有误`.
- `unconfigured`: `未接入`.

### Read-only Configuration Dialog

Triggered by the connected/configured card's `配置` menu item.

Behavior:

- Does not call begin registration.
- Does not show QR.
- Does not allow editing.
- Shows AppKey, masked AppSecret, RobotCode, source, createdAt, and updatedAt.
- AppSecret `显示` button opens a second confirmation dialog.
- After confirmation, call `channel_reveal_secret('dingtalk')` and show full AppSecret in local component state.
- Clear revealed AppSecret when the dialog closes.

### Remove Confirmation

Triggered by the `移除` menu item.

Confirmation copy should clearly say:

- The DingTalk channel will be disconnected.
- Locally saved AppKey and AppSecret will be deleted.
- Reconfiguration will require scanning the QR code again.
- Existing chat history will be kept.

On confirm:

- Call `channel_remove_platform('dingtalk')`.
- Backend disconnects the stream, deletes credentials config, and emits unconfigured state.
- UI returns to only the `配置` button.

### Switch Behavior

Turning off:

- Call `channel_set_enabled('dingtalk', false)`.
- Backend disconnects stream and stores `enabled=false`.
- Credentials remain on disk.
- UI keeps more menu and switch, with badge `已配置 / 未连接`.

Turning on:

- Call `channel_set_enabled('dingtalk', true)`.
- Backend reads existing config, stores `enabled=true`, and starts connecting.
- UI moves through `connecting` to `connected`, or `configError` on failure.

## Backend API

### Commands

```ts
channel_get_platforms(): Promise<ChannelPlatformState[]>
channel_get_platform(platform: ChannelPlatform): Promise<ChannelPlatformState>
channel_begin_registration(platform: ChannelPlatform): Promise<ChannelRegistrationBeginResult>
channel_poll_registration(platform: ChannelPlatform, deviceCode: string): Promise<ChannelRegistrationPollResult>
channel_set_enabled(platform: ChannelPlatform, enabled: boolean): Promise<ChannelPlatformState>
channel_remove_platform(platform: ChannelPlatform): Promise<ChannelPlatformState>
channel_reveal_secret(platform: ChannelPlatform): Promise<{ appSecret: string }>
channel_get_conversations(platform?: ChannelPlatform): Promise<ChannelConversation[]>
```

First iteration behavior:

- `platform='dingtalk'`: implemented.
- Other platforms: return coming-soon state or a clear unsupported error for mutating commands.

### Registration Commands

`channel_begin_registration('dingtalk')`:

- Calls DingTalk OPEN_CLAW registration init and begin.
- Request payload uses `source='OPEN_CLAW'`.
- Returns QR URL fields.

`channel_poll_registration('dingtalk', deviceCode)`:

- Calls DingTalk registration poll.
- On `waiting/fail/expired/unknown`, returns normalized poll state.
- On `success`, validates clientId and clientSecret.
- Saves config with `enabled=true`.
- Uses returned `robot_code` or AppKey fallback.
- Starts connection.
- Returns the updated platform state or a poll result containing enough config view fields for the dialog.

### State Events

Add or replace with:

```ts
channel:platform-state
payload: ChannelPlatformState
```

Emit when:

- Registration saves config.
- User enables or disables a platform.
- Connection state changes.
- Config error occurs.
- User removes a platform.
- App startup initializes or auto-connects a configured enabled platform.

Keep current message event semantics for incoming messages:

```ts
channel:message
```

## Backend Architecture

Target modules:

- `ChannelManager`: cross-platform facade for commands and events.
- `ChannelConfigStore`: user-scoped config persistence, secure secret handling, and platform state snapshots.
- `DingtalkChannelRuntime`: DingTalk stream lifecycle and message loop.
- `DingtalkRegistrationService`: OPEN_CLAW begin/poll logic.
- `ChannelSessionRouter`: existing session routing, updated to platform subdirectory paths.

This keeps platform-specific networking out of the generic channel store and keeps UI state aggregation out of the DingTalk stream client.

## Frontend Store

Replace single `dingtalkStatus` state with a platform map.

```ts
type ChannelStore = {
  platforms: Record<ChannelPlatform, ChannelPlatformState>
  conversations: ChannelConversation[]
  activeSessionId: string | null

  loadPlatforms(): Promise<void>
  loadPlatform(platform: ChannelPlatform): Promise<void>
  beginRegistration(platform: ChannelPlatform): Promise<ChannelRegistrationBeginResult>
  pollRegistration(platform: ChannelPlatform, deviceCode: string): Promise<ChannelRegistrationPollResult>
  setEnabled(platform: ChannelPlatform, enabled: boolean): Promise<void>
  removePlatform(platform: ChannelPlatform): Promise<void>
  revealSecret(platform: ChannelPlatform): Promise<string>
  loadConversations(platform?: ChannelPlatform): Promise<void>
}
```

Store rules:

- Platform state events update only the matching platform entry.
- Full AppSecret is never stored in the store.
- Read-only dialogs may keep revealed AppSecret in local component state only.

## Testing Plan

### Backend

- `UserScopedPaths` exposes platform directory paths:
  - `channels/dingtalk/config.json`
  - `channels/dingtalk/sessions.json`
- `ChannelConfigStore` writes config under the platform subdirectory.
- AppSecret is not persisted in plaintext when secure storage is available.
- `reveal_secret` decrypts and returns the original AppSecret.
- `set_enabled(false)` updates config to `enabled=false`, disconnects runtime, and keeps credentials.
- `set_enabled(true)` reads config and starts connection.
- `remove_platform` disconnects runtime, deletes credentials config, and returns unconfigured state.
- Registration success stores RobotCode from poll when present.
- Registration success falls back to AppKey as RobotCode when poll does not include RobotCode.
- Coming-soon platforms return non-mutating states and reject mutating commands clearly.

### Frontend

- Unconfigured DingTalk card shows only `配置`; no switch and no more menu.
- Registration dialog auto-starts OPEN_CLAW QR registration.
- Registration success hides QR and shows AppKey, masked AppSecret, and RobotCode.
- Connected/configured card shows more menu and switch.
- Connected/configured `配置` opens read-only dialog and does not call begin registration.
- AppSecret reveal requires confirmation and calls `revealSecret` only after confirmation.
- Closing the read-only dialog clears the revealed secret.
- `移除` opens confirmation; confirm calls remove and returns UI to the config-only state.
- Switch off calls `setEnabled(false)` and does not remove config.
- Switch on calls `setEnabled(true)` and reuses existing config.

### Verification Commands

## Implementation Sequence

1. Define domain types and new user-scoped platform paths.
2. Add `ChannelConfigStore` for new config schema, secret masking, reveal, remove, and enable flag updates.
3. Refactor `ChannelManager` to expose platform state commands and event emission.
4. Split DingTalk runtime lifecycle from generic channel state where needed.
5. Update registration success flow to save new schema and start enabled runtime.
6. Update Tauri commands and frontend IPC wrappers.
7. Update `channelStore` to platform map state.
8. Update `ChannelPage` card rendering and dialogs.
9. Update or split `ChannelConfig` into registration and read-only detail modes.
10. Add remove confirmation and AppSecret reveal confirmation.
11. Add frontend and backend targeted tests.
12. Run verification commands and fix failures using systematic debugging if needed.

## Open Decisions

None. Confirmed decisions:

- Use long-term Channel Domain model, not a minimal DingTalk-only patch.
- Do not fetch or display robot name.
- AppSecret is masked by default and revealed only after second confirmation.
- Switch disables/enables connection only; it does not delete credentials.
- Remove deletes AppKey/AppSecret and disconnects the channel.
- No legacy config migration is required because the feature has not shipped.
