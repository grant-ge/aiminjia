=== Step 1 — 诊断方法推荐 ===

## 目标

基于 Step 0 收集的症状数据和预加载的知识库，推荐最适合的诊断框架并获得用户确认。

## 成功标准

1. 症状归因分析覆盖所有 Step 0 记录的问题，无遗漏
2. 推荐框架有明确的选择理由，且与症状模式匹配
3. 重点分析维度已标注，用户理解诊断将聚焦哪些方面
4. 已了解用户过往尝试过的改善措施及效果
5. 用户明确确认诊断方向

## 执行步骤

系统已自动加载组织诊断知识库，结果在 [precompute_result] 中。
其中 frameworks 包含六盒子/7S/Burke-Litwin 三种诊断框架的维度、适用场景和评分方式；
interventions 包含各维度对应的干预措施库（含难度、周期、成本）。

基于 Step 0 收集的组织症状和知识库数据，推荐最适合的诊断框架。

1. 分析症状归因，判断主要问题集中在哪些维度：
   - 结构性问题（汇报关系、部门设置）→ 推荐六盒子 + 星型模型
   - 文化性问题（价值观、领导风格）→ 推荐7S框架
   - 流程性问题（协作、决策）→ 推荐六盒子
   - 综合性问题 → 推荐组合使用

2. 对推荐的框架说明：
   - 为什么选这个框架
   - 将如何应用（哪些维度重点分析）
   - 预期能发现什么

3. 用 save_analysis_note 保存诊断方法选择

询问用户：
- "这个诊断方向你认同吗？"
- "有没有已经尝试过但效果不好的改善措施？"
- "确认的话我就开始深入分析根因。"

## 约束

- 必须引用 Step 0 保存的症状数据，不得凭空推断
- 框架推荐不超过 2 种（除非症状确实高度复杂）
- 不在本步骤开始根因分析

## 异常处理

- **precompute_result 加载失败**：使用 base.md 中内置的框架知识进行推荐，告知用户知识库加载异常但不影响核心分析
- **Step 0 数据不充分**（某维度标记为"信息缺失"）：在推荐时标注该维度分析置信度较低，建议用户在 Step 2 深入分析前补充
- **用户不认同推荐框架**：询问用户的顾虑，解释其他框架的适用场景，根据用户偏好调整
- **用户要求使用不熟悉的框架**：坦诚说明该框架的局限性，建议作为补充而非主框架
